# AI Agent Skill: Release Launcher (Entry Point)

## 🎯 目的
本スキルは、GitHub Actions（およびVelopack）を活用した Chrome Profile Launcher の自動リリース作業、およびそれに付随するドキュメント更新や検証手順を定義します。リリースの安全かつ確実な実行とトレーサビリティの確保のため、本フローを厳密に遵守してください。

## 📝 トリガー
ユーザーから以下のような指示があった場合に、このスキルを起動・実行します。
* 「リリースを実行してください」
* 「新しいバージョン vX.Y.Z をリリースしてください」
* 「リリースの準備と実行をお願いします」

## 🛑 基本原則（絶対に守ること）
1. **プッシュ前の承認必須**: mainブランチへのすべてのプッシュ（README更新等）は、直前に変更内容を提示し、ユーザーの明示的な承認を得ること。（詳細：[RULES.md](./RULES.md)）
2. **タグの重複禁止**: 一度作成・プッシュしたタグは削除したり再利用したりしないこと。（詳細：[RULES.md](./RULES.md)）
3. **手動ビルドの排除**: 公式インストーラーは手動ビルドせず、必ず GitHub Actions 経由で生成されたアセットを使用すること。

---

## 🛠 前提環境（Prerequisites）
リリース前に、Git の権限や GitHub CLI (`gh`) の認証が完了していること、およびローカルテスト用の .NET 10.0 SDK が利用可能であることを確認してください。（詳細：[RULES.md](./RULES.md)）

---

## 🔄 実行フロー（ステップ・バイ・ステップ）
以下のステップを順番に実行し、各ステップが完了するごとにユーザーに状況を報告してください。詳細な作業最適化については、[OPTIMIZATION.md](./OPTIMIZATION.md) を参照して作業を分散させることができます。

### Step 0: 環境チェック & ローカル検証
1. **Git 状態の確認**:
   ```bash
   git status
   git branch --show-current
   ```
   - 未コミットの変更がある場合や、`main` 以外のブランチにいる場合はユーザーに報告し、指示を仰ぐ。
2. **ローカルビルド & テストの実行**:
   ```bash
   dotnet test
   ```
   - すべての自動テストが正常にパスすることを確認する。テストが失敗した場合は、リリースを中断してユーザーに修正案を提示する。（詳細：[ERROR_HANDLING.md](./ERROR_HANDLING.md)）

### Step 1: リリースバージョンの決定
1. セマンティックバージョニング（例: `v1.0.0`）に基づき、リリースするバージョン番号を決定し、ユーザーと合意を取る。

### Step 2: バージョンタグの作成とプッシュ（承認必須）
1. ローカルでバージョンタグを作成する。
   ```bash
   git tag vX.Y.Z
   ```
2. **重要**: タグのプッシュ前にユーザーに変更予定内容を提示し、明示的な承認を得る。
3. 承認後、タグをリモートにプッシュする。
   ```bash
   git push origin vX.Y.Z
   ```

### Step 3: GitHub Actionsの監視
1. GitHubの `Release` ワークフローの進捗を監視する。（サブエージェント等への監視タスク分散は [OPTIMIZATION.md](./OPTIMIZATION.md) を参照）
   - `gh run list --workflow=release.yml`（またはGitHub ActionsのWeb UI）で、プッシュされたタグに対応する実行状況を確認。
2. 完了するまで待ち、エラーなく終了したこと（インストーラー等のアセットが正常に生成され、ドラフトまたはリリースが作成されたこと）を確認する。

### Step 4: README.md のダウンロードリンク更新
1. `README.md` のダウンロードリンクおよびバージョン表記を、今回リリースした新しいタグバージョン（URLおよびテキスト）に更新する。
   - 対象箇所：ダウンロードリンクのURL（`.../releases/download/vX.Y.Z/ChromeProfileLauncher-win-Setup.exe`）およびバージョン注釈。
2. **プッシュ前の承認必須ルールに基づき、変更内容をユーザーに提示して明示的な承認を得る。**
3. 承認後、mainブランチにコミットおよびプッシュを行う。
   ```bash
   git add README.md
   git commit -m "docs: READMEのダウンロードリンクを vX.Y.Z に更新"
   git push origin main
   ```

### Step 5: リリースノートの編集・公開
1. GitHub Releases 上にドラフト作成されたリリースの詳細（変更履歴、主なアップデート項目など）をまとめ、リリースノートのドラフトテキストをユーザーに提案する。
2. ユーザーの確認・承認後、GitHub CLI またはブラウザ経由でリリース内容を確定（公開）する。
   - コマンド例:
     ```powershell
     chcp 65001; gh release edit vX.Y.Z --draft=false --title "vX.Y.Z - [リリース名]" --notes "[リリースノート内容]"
     ```

### Step 6: 自動アップデートの動作確認
1. 既に古いバージョンがインストールされている環境があれば、アプリを起動して3秒後に自動アップデート検知ダイアログが表示されるか、更新が正常に行われるかをユーザーに検証してもらう。
