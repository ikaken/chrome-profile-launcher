# AI Agent Skill: Issue Handling Workflow

## 🎯 目的
AIエージェントがGitHubのIssue対応を行う際の、設計・実装・ドキュメント・Git運用の標準フローを定義します。品質とトレーサビリティを担保するため、このフローを厳密に遵守してください。

## 📝 トリガー
ユーザーから「Issue番号 #◯◯ に対応して」または「イシューの対応を開始して」と指示された場合に、このスキルを起動・実行します。

## 🛑 基本原則（絶対に守ること）
1. **直接コミットの禁止**: `main` ブランチへ直接コミットしないこと。
2. **Issue単位の管理**: 変更は必ずIssue単位の作業ブランチで管理すること。
3. **ドキュメントの同期**: ドキュメント（仕様書・設計書・テスト仕様書）は常に最新の実装状態と一致させること。
4. **履歴の保存**: 変更理由や設計上の判断（なぜそうしたか）は必ずドキュメントに記録すること。

---

## 🛠 前提環境（Prerequisites）
このスキル（ワークフロー）を実行・運用するにあたり、以下の環境が整っていることを確認してください。

1. **Git**
   - バージョン管理およびリポジトリ操作（ブランチ作成、コミット、プッシュ）のために必須です。
   - 初期設定（`user.name`, `user.email`）およびリモートリポジトリへの認証が完了していること。
2. **GitHub CLI (`gh`)** （推奨）
   - コマンドラインからのIssue詳細確認やPull Requestの自動作成（Step 11）をスムーズに行うために有用です。
   - 認証（`gh auth login`）が完了していること。

---

## 🔄 実行フロー（ステップ・バイ・ステップ）
以下のステップを順番に実行し、各ステップが完了するごとにユーザーに状況を報告してください。

### Step 0: 環境チェック【自動実行】
スキル起動時に、以下のコマンドを実行して前提環境が整っているか自動的に確認する。
1. **Git の確認**:
   ```bash
   git --version
   git config user.name
   git config user.email
   git remote -v
   ```
   - いずれかが未設定・失敗の場合、ユーザーに設定を依頼して中断する。
2. **GitHub CLI の確認**（利用可能な場合）:
   ```bash
   gh auth status
   ```
   - 認証されていない場合、`gh auth login` の実行を案内する。未インストールの場合はスキップし、Step 11 では手動PR作成の案内に切り替える。
3. **リポジトリ状態の確認**:
   ```bash
   git status
   git branch --show-current
   ```
   - 未コミットの変更がある場合や、想定外のブランチにいる場合はユーザーに報告し、指示を仰ぐ。

### Step 1: Issue内容の確認と明確化
1. 指定されたIssueの内容を読み込む。
2. 要件を理解し、不明点や考慮すべきエッジケースがあれば洗い出す。
3. 必要に応じて、ユーザーに質問して仕様を確定させるか、Issueにコメントして補足する。

### Step 2: 作業用ブランチの作成
1. 以下の命名規則に従い、ブランチを作成してチェックアウトする。
   ```bash
   git checkout -b feature/{issue番号}-{内容の英単語}
   ```
   *(例: `git checkout -b feature/012-profile-sort`)*

### Step 3: 変更履歴（changes）ドキュメントの初期化【必須】
1. `docs/changes/` ディレクトリに以下の名前でファイルを作成する。
   ```text
   docs/changes/{issue番号}-{内容の英単語}.md
   ```
2. 以下のテンプレートを展開し、初期状態を記述する。
   ```markdown
   # {Issueタイトル}

   ## 背景
   ## 目的
   ## 変更内容
   ## 影響範囲
   ## 非対応
   ## 備考
   ```

### Step 4: 設計と方針の策定
1. 実装方針を決定し、Step 3で作成した `changes` ファイルに記録する。
2. アーキテクチャやデータ構造に変更がある場合は、事前に `docs/design_document.md` などの更新案を検討し、ユーザーと合意を取る。

### Step 4.5: 人間による設計レビュー（必須）
1. ユーザーに対して、決定した設計方針と `docs/changes/` の記述内容を報告し、確認を求める。
2. ユーザーから「実装開始」または「OK」の指示が出るまで、次のステップ（実装）へ進んではならない。

### Step 5: 実装
1. 決定した設計方針に基づいてコードを変更する。
2. 変更はなるべく小さく分割し、意味のある単位で進める。

### Step 6: コミット
1. 実装がひと段落するごとにコミットする。
   ```bash
   git add .
   git commit -m "{prefix}: {日本語での変更内容}"
   ```
2. コミットメッセージのprefix規約:
   - `feat` : 機能追加
   - `fix` : バグ修正
   - `refactor` : リファクタリング
   - `docs` : ドキュメントの変更

### Step 7: 実装中のドキュメント随時更新
1. 実装中に生じた設計変更や重要な判断は、必ず `changes` ファイルに追記する。

### Step 8: テスト・動作確認
1. 変更した機能の動作確認を行う。
2. エッジケースがカバーされているか確認する。
3. 必要に応じてテストコードの実装、および `docs/test_specification.md` の更新を行う。

### Step 8.5: 人間による実装・テスト確認（必須）
1. ユーザーに対して、実装内容とテスト結果を詳細に報告し、確認を求める。
2. ユーザーから「ドキュメント更新へ進む」または「OK」の指示が出るまで、次のステップへ進んではならない。

### Step 9: 最終ドキュメントの反映【必須】
実装完了後、プロジェクトの主要ドキュメントに今回の変更内容を完全に反映させる。
1. `docs/` ディレクトリ内を走査し、以下のカテゴリに該当するドキュメントを特定する:
   - **仕様書**: 機能仕様や要件を記述したドキュメント（最新仕様への更新）
   - **設計書**: アーキテクチャやデータ構造を記述したドキュメント（設計変更の反映）
   - **テスト仕様書**: テスト項目や手順を記述したドキュメント（テスト項目の追加・更新）
2. 該当するドキュメントが見つからない場合は、ユーザーに更新対象を確認する。
> **注意**: `docs/changes/` 配下のファイルは履歴として残すため削除しないこと。

### Step 10: リポジトリへのPush
1. 以下のコマンドでリモートにPushする。
   ```bash
   git push origin feature/{branch名}
   ```

### Step 11: Pull Requestの作成
1. Pull Requestを作成する（またはユーザーにPR作成のための情報を提示する）。
2. PRのDescription（概要）には以下を必ず含める:
   - `Fixes #{Issue番号}` （Issueの自動クローズ用）
   - `docs/changes/{...}.md` への参照リンク
   - 変更の概要説明

---

## ⚠️ エラーハンドリング・中断ポリシー
ステップ実行中に問題が発生した場合、エージェントは以下のルールに従ってください。

| 状況 | 対応 |
|---|---|
| 環境チェック失敗（Step 0） | ユーザーに不足している設定・ツールを案内し、**スキルを中断**する |
| ビルドエラー（Step 5） | エラー内容を分析し修正を試みる。3回試行しても解決しない場合は、エラーログを添えてユーザーに報告し**指示を仰ぐ** |
| テスト失敗（Step 8） | 失敗したテストの原因を分析し修正を試みる。テスト自体の仕様変更が必要な場合はユーザーに確認する |
| Push / PR 作成失敗（Step 10-11） | 認証エラーやネットワーク問題を切り分け、ユーザーに報告する。`gh` が利用できない場合は手動操作の手順を案内する |
| ユーザーから中断指示 | 現在の作業状態を `docs/changes/` に記録し、途中経過をコミットしてから中断する |

---

## ✅ 必須チェックリスト
作業完了（Step 11）前に、エージェントは以下の項目を自己評価し、すべてクリアしていることを確認してください。

- [ ] `main` ブランチで直接作業していないか？
- [ ] `docs/changes/` ディレクトリに今回のIssue用の変更ドキュメントが作成・更新されているか？
- [ ] 仕様書・設計書・テスト仕様書などの主要ドキュメントが、今回の実装内容に合わせて更新されているか？
- [ ] コミットメッセージの規約（prefix）は正しく守られているか？
- [ ] Issueとの紐付け（Fixes #番号）が行われているか？
