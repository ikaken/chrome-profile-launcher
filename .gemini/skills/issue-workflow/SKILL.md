# Issue Handling Workflow

GitHubのIssue対応を行う際の、設計・実装・ドキュメント・Git運用の標準フローです。
品質とトレーサビリティを担保するため、このフローを厳密に遵守してください。

## 🛑 基本原則
- **直接コミット禁止**: `main` ブランチへ直接コミットしないでください。
- **ブランチ管理**: 必ずIssue単位の作業ブランチ (`feature/{issue_no}-{desc}`) を作成してください。
- **ドキュメント第一**: 実装と同時に `docs/changes/` を作成し、仕様書・設計書・テスト仕様書を常に最新に保ってください。

## 🔄 実行フロー

### 1. Issueの明確化と準備
- 指定されたIssueの内容を読み込み、要件とエッジケースを洗い出す。
- `git checkout -b feature/{issue_no}-{desc}` で作業ブランチを作成する。

### 2. 変更履歴の初期化
- `docs/changes/{issue_no}-{desc}.md` を作成し、以下の情報を記述する：
  - 背景、目的、変更内容（予定）、影響範囲。

### 3. 設計・実装・コミット
- 実装方針を決定し、`docs/changes/` に記録する。
- 意味のある単位でコードを変更し、prefix規約（`feat`, `fix`, `refactor`, `docs`）を守ってコミットする。
- 実装中に生じた設計変更や重要な判断は、随時 `docs/changes/` に追記する。

### 4. テストとドキュメント同期
- 動作確認を行い、必要に応じてテストコードを追加する。
- 以下のドキュメント群に今回の変更内容を完全に反映させる：
  - `docs/chromeプロファイルランチャ仕様書（wpf最終版）.md`
  - `docs/design_document.md`
  - `docs/test_specification.md`

### 5. Pushとプルリクエスト作成
- 変更をプッシュし、プルリクエストを作成する。
- PRの説明には以下を必ず含める：
  - `Fixes #{issue_no}`
  - `docs/changes/` へのリンク
  - 変更の概要

## ✅ 完了チェックリスト
- [ ] `main` ブランチではなく作業ブランチで作業したか？
- [ ] `docs/changes/` が作成・更新され、実装理由が記録されているか？
- [ ] すべての主要ドキュメントが実装内容と同期しているか？
- [ ] コミットメッセージの prefix は正しいか？
- [ ] PR に `Fixes #番号` が含まれているか？
