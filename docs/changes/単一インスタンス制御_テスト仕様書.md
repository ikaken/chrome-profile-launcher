# 単一インスタンス制御 テスト仕様書

## 概要
本テスト仕様書は、Chrome Profile Launcher における「単一インスタンス制御（多重起動防止）」機能（Issue #5）が正しく動作することを検証するためのものです。
現在実装済みの Phase 1 (Mutex + FindWindow 方式) および 今後実装予定の Phase 2 (Named Pipe IPC 方式) の両方を対象とします。

---

## テスト環境
- **OS**: Windows 10 / 11
- **実行形式**: デバッグビルド (`dotnet run -c Debug`) およびリリースビルド (`.exe` 直接起動)

---

## テストケース一覧

### 1. 新規起動テスト（正常系）
**目的**: アプリケーションが単独で正常に起動し、単一インスタンス用の準備が完了することを確認する。

| テストID | テスト手順 | 期待される結果 | 備考 |
|----------|------------|----------------|------|
| T-001 | アプリケーションが起動していない状態で、`ChromeProfileLauncher.exe` を起動する。 | メインウィンドウが正常に表示される。ログに Mutex 取得成功が記録される。 | |
| T-002 | アプリケーションを終了する。 | ウィンドウが閉じ、プロセスが完全に終了する。Mutex が解放される。 | |

### 2. 多重起動防止テスト（正常系）
**目的**: 既にアプリが起動している状態で、再度起動しようとした際の制御が正しく行われるか確認する。

| テストID | テスト手順 | 期待される結果 | 備考 |
|----------|------------|----------------|------|
| T-003 | アプリを起動した状態で、さらに別の `ChromeProfileLauncher.exe` を起動する。 | 2つ目のアプリは起動せず即座に終了する。1つ目のアプリのウィンドウがアクティブ（最前面）になる。 | |
| T-004 | アプリを起動し、メインウィンドウを「最小化」する。その後、別インスタンスを起動する。 | 2つ目のプロセスが終了し、最小化されていた1つ目のウィンドウが元のサイズに復元され、最前面に表示される。 | Phase1/2 共通 |
| T-005 | コマンドラインや別ディレクトリから起動する。 | 同様に二重起動がブロックされ、既存のウィンドウが前面に表示される。 | |

### 3. IPC通信テスト（Phase 2: 正常系）
**目的**: Named Pipe を介したプロセス間通信が想定通りに動作することを確認する。

| テストID | テスト手順 | 期待される結果 | 備考 |
|----------|------------|----------------|------|
| T-006 | アプリ起動中に、別インスタンスを起動する。 | IPC 経由で `ACTIVATE` コマンドが送信され、既存インスタンス側で受信される。ログに送受信の記録が残る。 | |
| T-007 | アプリ起動中に、別インスタンスを複数回連続で起動する（ダブルクリックを連打するなど）。 | 全ての追加インスタンスが既存のパイプに接続してメッセージを送り、即座に終了する。既存インスタンスがクラッシュしない。 | |

### 4. ゾンビプロセス・異常系テスト（Phase 2: 異常系）
**目的**: 既存プロセスが応答不能な状態（ゾンビプロセス）に陥っている場合でも、新しいプロセスが正常に起動できることを確認する。

| テストID | テスト手順 | 期待される結果 | 備考 |
|----------|------------|----------------|------|
| T-008 | PowerShell 等の別スクリプトを使用し、`Global\ChromeProfileLauncher-SingleInstance-Mutex` を保持したダミープロセスを立ち上げる（または IPC サーバーを立てない状態を作る）。その後、本アプリを起動する。 | アプリは Mutex 取得に失敗して IPC 送信を試みるが、200ms 後にタイムアウトとなる。タイムアウト後、異常検知として通常通りアプリが起動しウィンドウが表示される。 | |
| T-009 | 既存プロセスをデバッガでブレーク（一時停止）し、応答できない状態にする。その後、別インスタンスを起動する。 | 200ms のタイムアウトを経て、2つ目のインスタンスが強制的に（通常通り）起動する。 | |
| T-010 | Mutex は解放されているが、前回終了時のゴミプロセス（ウィンドウなし）が残存している場合。 | 通常通り新規起動として処理され、新たな Mutex を取得して正常起動する。 | Phase 1での課題に対するテスト |

### 5. パフォーマンス・負荷テスト
**目的**: 単一インスタンス制御や IPC 通信がアプリの起動速度に悪影響を与えていないことを確認する。

| テストID | テスト手順 | 期待される結果 | 備考 |
|----------|------------|----------------|------|
| T-011 | アプリの新規起動時間を計測する。 | IPC非対応版（Phase 1）とほぼ変わらない時間でメイン画面が表示されること。 | |
| T-012 | 正常な二重起動発生時のオーバーヘッドを計測する。 | 起動操作から既存ウィンドウが最前面に現れるまでの遅延が、ユーザーが気にならないレベル（数ms〜数十ms）であること。 | |
| T-013 | ゾンビプロセス検知（タイムアウト）発生時の起動時間を計測する。 | 通常の起動時間に加え、設定されたタイムアウト時間（約200ms）の遅延のみで起動すること。不自然に長く固まらないこと。 | |

---

## 実施基準と完了条件
- 全てのテストケースにおいて期待される結果が得られること。
- ログ（`debug.log`）に各フェーズの重要な情報（Mutex取得状況、IPC送信結果、エラーなど）が適切に出力されていること。
- テスト実行中にアプリのクラッシュや未処理の例外が発生しないこと。
