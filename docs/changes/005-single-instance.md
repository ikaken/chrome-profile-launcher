# Issue #5: 多重起動しないでほしい

## 背景
現在、アプリを複数起動することが可能であり、ユーザーが誤って複数のウィンドウを開いてしまう可能性がある。
また、Mutex のみによる制御では、デバッグ時の強制停止等でゾンビプロセスが残存した場合に新規起動が阻害される問題がある。

## 目的
- アプリを単一インスタンス（Single Instance）に制限し、二重起動を防止する
- 二重起動が試みられた際には、既に起動しているウィンドウを最前面に表示する
- ゾンビプロセスによる起動阻害を回避する
- 起動速度への影響を最小化する

## 現在の実装詳細（Phase 2: IPC対応版）

### Mutex による二重起動チェック
- `System.Threading.Mutex` を使用して、アプリケーション全体で一意な名前 (`Global\ChromeProfileLauncher-SingleInstance-Mutex`) でロックを取得。
- セッションを跨いで有効にするため `Global\` プレフィックスを付与。

### IPC（Named Pipe）による生存確認とアクティブ化
- 既存インスタンスが既に Mutex を保持している場合、Named Pipe (`ChromeProfileLauncher-SingleInstance-Pipe`) 経由で `ACTIVATE` メッセージを送信。
- タイムアウト（200ms）を設定し、応答がない場合は既存プロセスが異常（ゾンビプロセス）と判断して自プロセスをプライマリとして起動を継続する。

### 既存インスタンス側処理
- 非同期で Named Pipe サーバーを待機。
- メッセージ受信時に Dispatcher 経由で `MainWindow` を復元・アクティブ化。
- `Topmost` を一時的に制御することで確実に最前面へ表示。

### 終了時の処理
- `OnExit` で Named Pipe サーバーの停止（CancellationToken）および Mutex の解放を行う。

## Phase 2 設計: Named Pipe IPC 方式

### 基本方針
従来の Mutex のみの制御から、IPC（Named Pipe）を組み合わせた「生存確認付き単一インスタンス制御」に移行する。

### 起動フロー

#### 1. 新規起動時（通常）
1. アプリ起動
2. Mutex 取得（成功）
3. Named Pipe サーバー起動（非同期）
4. MainWindow 生成・表示

※ 待ち時間なし

#### 2. 二重起動時（正常）
1. Mutex 取得失敗
2. 既存インスタンスへ IPC メッセージ送信
3. 応答受信（即時）
4. 自プロセス終了

既存インスタンス側：
- ウィンドウを復元（最小化解除）
- 最前面化

#### 3. 二重起動時（ゾンビプロセス）
1. Mutex 取得失敗
2. IPC 送信
3. タイムアウト待機（200ms）
4. 応答なし → 既存インスタンス異常と判断
5. 自プロセスを通常起動

### IPC 仕様

| 項目 | 内容 |
|------|------|
| 通信方式 | Named Pipe（ローカルプロセス間通信） |
| 送信コマンド | `ACTIVATE` |
| タイムアウト | 200ms（調整可能） |

### 既存インスタンス側処理（受信時）
- メインスレッドで実行（Dispatcher 使用）

処理内容：
1. ウィンドウが最小化されている場合は復元
2. ウィンドウをアクティブ化
3. 一時的に Topmost を true にして前面化
4. フォーカスを設定

### Mutex 仕様

| 項目 | 内容 |
|------|------|
| 名前 | `Global\ChromeProfileLauncher-SingleInstance-Mutex` |
| 目的 | 同時起動の入口制御 |

### パフォーマンス要件

| ケース | 影響 |
|--------|------|
| 新規起動 | 従来と同等（影響なし） |
| 二重起動（正常） | +数ms |
| ゾンビ検知時 | 最大 +200ms |

### 例外・異常系対応

- **ゾンビプロセス対策**: IPC 応答がない場合は無視して起動継続
- **デバッグ時の考慮**: 強制停止時にプロセスが残存する可能性あり
  - OnExit で Mutex 解放
  - 必要に応じて DEBUG 時は単一インスタンス制御を無効化
