# Chromeプロファイル管理・制御 完全統合報告書

---

## 1. 概要

本報告書は、Google Chromeにおけるプロファイル単位の管理・制御について、以下の課題を解決するための技術設計を網羅的にまとめたものである。

### 対象課題

- 起動中プロファイルの一覧取得
- 同一プロファイルの多重起動防止
- 既存ウィンドウへのフォーカス制御
- 外部起動を含めた整合性確保

---

## 2. Chromeの仕様と制約

Chromeは以下の特性を持つ。

- **マルチプロセス構造**：renderer / gpu / utility など多数の子プロセスが生成される
- **既存プロセスの再利用**：新規起動時に既存プロセスへ処理が委譲される（プロセスが増えない場合がある）
- **プロファイル情報の非露出**：プロファイル情報がプロセス・ウィンドウに明示的に保持されない

これにより、外部からプロファイルとウィンドウを直接対応付けることは困難である。

---

## 3. 各技術の詳細解説

---

### 3.1 起動パラメータ管理（--profile-directory）

#### 基本概念

```
chrome.exe --profile-directory="Profile 1"
```

起動時専用の指示パラメータ。Chromeの内部でUser Data Directory配下の該当ディレクトリを参照し、プロファイルごとに独立したセッションを構築する。

#### 内部挙動

| 状況 | 挙動 |
|---|---|
| Chromeが未起動 | 新規プロセスを生成（期待通り） |
| Chromeがすでに起動中 | 既存プロセスへ処理を委譲（新規プロセスは作られない） |

起動後にパラメータは保持されない。

#### メリット

- 起動意図が100%明確
- 実装が非常にシンプル
- プロファイル切替UIを使わなくてよい（自動化向き）

#### デメリット

- 起動後に情報が消える（パラメータは「記録されない」）
- プロファイル識別に使えない
- プロセスと紐付かない
- 既存プロセスに吸収される

#### なぜそれでも必須か

- 「起動時の意図」を保証するため
- ランチャーの入口として最適（起動制御の起点）
- 他の仕組み（PID管理など）と組み合わせやすい

#### 正しい使い方（設計）

```
❌ NGな使い方：起動パラメータだけで全部管理する → 破綻する

✔ 正しい使い方：
  起動パラメータ = 「トリガー」
  ＋
  別の手段で状態管理
```

#### 評価

> **必須（起動トリガー）だが、単独利用は不可**

### 3.2 PID管理

#### 基本概念

PID（Process ID）は、OSがプロセスに割り当てる一意の番号。Win32 API / WMI により取得可能。

#### できること / できないこと

| 操作 | 可否 |
|---|---|
| ウィンドウフォーカス | ○ |
| プロセス生存確認 | ○ |
| 強制終了 | ○ |
| プロファイル識別 | × |
| ウィンドウ識別（単独） | △ |

#### メリット

- OSレベルで確実に扱える
- ウィンドウ操作（フォーカス）が可能
- プロセスの生存確認が可能
- Windows API で制御可能（PowerShell / C# / Python 等）

#### デメリットと本質的問題

**問題①：Chromeのプロセス再利用**

```
Profile 1 → PID 1000
Profile 2 → PID 1000（同じ）
```

同じPIDに複数プロファイルが吸収されるため判別不能になる。

**問題②：PIDの揮発性**

```
昨日：PID 24076
今日：PID 18032
```

PC再起動やChrome再起動でPIDは完全に変わる。保存しても意味がなくなる。

**問題③：複数ウィンドウ問題**

```
PID 24076
 ├ Window A（Profile 1）
 ├ Window B（Profile 2）
 └ Window C（Profile 1）
```

PIDだけではウィンドウが特定できない。

**問題④：子プロセス多数**

```
--type=renderer
--type=gpu-process
--type=utility
```

Chromeは大量の子プロセスを生成するため、どれが本体か判断が必要になる。

#### 精度を上げるテクニック

**差分検出（推奨）**
```
起動前のPID一覧
起動後のPID一覧
差分 = 新規プロセス → これが最も確実
```

**親プロセスを見る**
```powershell
Get-CimInstance Win32_Process
# ParentProcessId で関係を追う
```

**メインウィンドウだけ抽出**
```powershell
Where-Object { $_.MainWindowHandle -ne 0 }
```

#### 実用的な使い方

```powershell
# ① 起動直後にPIDを取得
$p = Start-Process "chrome.exe" "--profile-directory=`"Profile 1`"" -PassThru
$pid = $p.Id

# ② 少し待ってウィンドウを掴む
Start-Sleep -Milliseconds 500
(Get-Process -Id $pid).MainWindowHandle

# ③ 管理テーブルに保存
{
  "Profile 1": {
    "pid": 24076,
    "lastSeen": "2026-04-13T10:00:00"
  }
}
```

#### 評価

> **操作用として必須だが、単独での識別用途は不可**

### 3.3 LOCKファイル

#### 概要

プロファイルディレクトリ内に生成されるロックファイル（SingletonLock 等）を利用する方式。Chrome起動時に生成される内部機構。

#### メリット

- プロファイル単位での起動状態判定が可能
- 外部から確認できる
- Chrome内部仕様に依存しない

#### デメリット

- ウィンドウとの紐付け不可
- 異常終了時に残存する可能性（不整合が発生する）

#### 評価

> **起動状態判定に有効**

---

### 3.4 プロセス差分検出

#### 概要

起動前後のプロセス一覧の差分から新規プロセスを特定する方式。

#### なぜ差分検出が必要か

- `--profile-directory` は残らない
- PIDは使い回されることがある
- プロファイル識別できない
- → 「どのPIDが今回の起動か分からない」

#### 考え方と実装

```
① 起動前のChromeプロセス一覧を取得
② Chromeを起動
③ 起動後のプロセス一覧を取得
④ 差分 = 新しく増えたプロセス
```

**イメージ**
```
起動前: PID 1000, PID 1001
起動後: PID 1000, PID 1001, PID 1050 ← NEW
→ 1050 が今回の起動
```

#### なぜ精度が高いのか

- OSレベルで確定できる（実際に増えたプロセスを見ている）
- Chromeの内部仕様に依存しない
- リアルタイム性がある（起動直後に取得するためブレが少ない）

#### 注意点：複数プロセス同時生成問題

```
差分:
PID 2000 (browser)
PID 2001 (renderer)
PID 2002 (gpu)
PID 2003 (utility)
→ どれが本体？
```

**解決方法：メインプロセスだけ選別する**

| 条件 | 内容 |
|---|---|
| `--type` が無い | これが「ブラウザ本体」 |
| `MainWindowHandle -ne 0` | ウィンドウを持つプロセス |
| `StartTime` が最新 | 起動タイミングが一番近い |

#### PowerShell実装例

```powershell
# ① 起動前取得
$before = Get-CimInstance Win32_Process -Filter "Name = 'chrome.exe'" |
  Select-Object ProcessId

# ② 起動
Start-Process "chrome.exe" "--profile-directory=`"Profile 1`""
Start-Sleep -Milliseconds 500

# ③ 起動後取得
$after = Get-CimInstance Win32_Process -Filter "Name = 'chrome.exe'" |
  Select-Object ProcessId, CommandLine

# ④ 差分抽出
$new = $after | Where-Object {
    $before.ProcessId -notcontains $_.ProcessId
}

# ⑤ 本体だけ選別（--type が付いていないもの）
$main = $new | Where-Object {
    $_.CommandLine -notmatch "--type="
}
```

#### さらに精度を上げる方法

```powershell
# 方法①：時間でフィルタ
(Get-Process).StartTime  # 一番新しいものを採用

# 方法②：ウィンドウありだけ
Get-Process chrome | Where-Object {
    $_.MainWindowHandle -ne 0
}

# 方法③：組み合わせ（最強）
# 差分 ＋ typeなし ＋ windowあり ＋ 最新 → ほぼ確定
```

#### 落とし穴

| 問題 | 内容 |
|---|---|
| 待ち時間が短すぎる | プロセス生成が間に合わない |
| 他のChrome操作と競合 | 同時にタブ開くとズレる |
| Chromeが既に起動中の場合 | 新規プロセスが増えないこともある |

**差分がない場合の対策**
```
差分が無い
 ↓
既存プロセスに吸収された
 ↓
ウィンドウ差分で検出（次節参照）
```

#### 評価

> **現実的に最も信頼できるPID取得手法**

### 3.5 ウィンドウ差分検出

#### 概要

ウィンドウ一覧の差分から新規ウィンドウを特定する方式。

```
起動前: Chromeウィンドウ一覧取得
起動後: 再取得
差分: 新規ウィンドウ（hwnd）
```

#### メリット

- ユーザー視点で最も直感的・安定的
- プロセスより正確な場合がある
- 実用上最も安定

#### デメリット

- 既存ウィンドウの再利用時に検出不可
- 外部起動を認識できない
- 実装難易度がプロセス差分より高い

#### プロセス差分とのハイブリッド

```
プロセス差分 ＋ ウィンドウ差分
= ほぼ100%安定
```

#### 評価

> **メイン手法として最適**

---

### 3.6 AUMID（AppUserModelId）

#### 概要

Windowsがアプリケーションを識別するためのID。タスクバー・通知システムで利用。

#### Chromeでの挙動

- 全ウィンドウで同一AUMID
- プロファイル間で差異なし

#### 例外

PWA（`--app` 起動）では別AUMIDになる場合あり。

#### 評価

> **プロファイル識別には使用不可**

## 4. 最適アーキテクチャ

### 4.1 管理情報の構成

| 情報 | 役割 |
|---|---|
| プロファイル名 | キー（識別子） |
| hwnd（ウィンドウハンドル） | フォーカス制御のメイン |
| PID | 補助（操作用） |
| LOCK状態 | 起動判定 |

### 4.2 管理データ構造例

```json
{
  "Profile 1": {
    "pid": 24076,
    "hwnd": 131234,
    "lockExists": true,
    "lastSeen": "2026-04-13T10:00:00"
  }
}
```

### 4.3 起動フロー

```
① 起動要求
② LOCKファイル確認
   ├ 起動中 → 既存ウィンドウ探索 → hwndでフォーカス
   └ 未起動 → 起動処理へ
③ --profile-directory を指定して起動
④ ウィンドウ差分検出（メイン）
⑤ プロセス差分検出（補助）
⑥ hwnd・PIDを保存
```

### 4.4 フォーカス制御

```
hwnd取得
↓
WinActivate（AHK）/ SetForegroundWindow（Win32 API）
```

### 4.5 強化版運用フロー

```
起動前：LOCK確認
起動時：--profile-directory 指定
起動後：PID記録 / hwnd記録
運用中：PID監視 / ウィンドウ監視
```

---

## 5. 多重起動防止戦略

- LOCKファイルで起動状態を事前判定
- 起動中の場合は新規起動を行わず、既存ウィンドウへフォーカス
- 既存ウィンドウがあれば再利用
- ウィンドウ差分で補完

## 6. 実装コードの評価（AHKスクリプト）

採用技術：

- 起動パラメータ（`--profile-directory`）
- ウィンドウ差分検出（メイン）
- hwnd管理（プロファイル紐付け）

特徴：

- シンプルかつ高速
- Chromeのプロセス再利用問題を回避
- ウィンドウ単位で管理

課題：

- 外部起動ウィンドウを認識できない
- 既存ウィンドウの再利用時に検出失敗
- 永続性がない（セッション限定）

> **評価：実用レベル（高品質）**

## 7. 各手法の最終比較

| 手法 | 役割 | 強み | 弱み | 評価 |
|---|---|---|---|---|
| 起動パラメータ | 起動トリガー | シンプル・確実に起動指定 | 情報が残らない・識別不可 | 必須（単独不可） |
| PID管理 | ウィンドウ操作・監視 | OS標準・フォーカス可能 | 識別不可・揮発・再利用問題 | 補助必須（単独不可） |
| LOCKファイル | 起動状態判定 | プロファイル単位で確実 | ウィンドウ紐付け不可 | 状態判定に有効 |
| プロセス差分検出 | 新規PID特定 | 高精度・仕様非依存 | 複数プロセス・タイミング依存 | 最良のPID取得手法 |
| ウィンドウ差分検出 | 新規ウィンドウ特定 | 実用的・安定 | 再利用時検出不可 | メイン手法 |
| AUMID | （参考） | Chromeウィンドウ判定には利用可 | プロファイル識別不可 | プロファイル管理では不採用 |

---

## 8. 最終結論

Chromeの仕様上、単一手法による完全なプロファイル管理は不可能である。

### 最適構成（ハイブリッド方式）

| フェーズ | 使用技術 |
|---|---|
| 起動制御 | `--profile-directory` |
| メイン検出 | ウィンドウ差分検出 |
| 補助検出 | プロセス差分検出 |
| ウィンドウ操作 | PID / hwnd |
| 状態判定 | LOCKファイル |

> **この構成により、実用上ほぼ完全なプロファイル管理が実現可能である。**
