# 起動済みプロファイルへのフォーカス機能の改善計画

既に起動しているChromeプロファイルを選択した際、既存のウィンドウにフォーカスが当たらず新しいウィンドウが開いてしまう問題（Issue #2）を解決するための計画です。

## 概要
本プロジェクトは、以下の5つのフェーズで慎重に進行します。各フェーズの完了時、または重要な判断が必要なタイミングでユーザーに報告します。

1. **調査フェーズ（原因解析）** ← 完了
2. **設計・実現性調査フェーズ（対応方針決定）** ← 完了
3. **実装フェーズ**
4. **検証フェーズ（単体・結合テスト）**
5. **完了報告・納品**

## 調査フェーズ（原因解析）の結果
実機環境でのプロセス調査により、以下の問題が特定されました。

### 問題1. 「Default」プロセスの誤検知（False Positives）
現在の判定ロジック（`LauncherService.cs` 68-69行目）では `--profile-directory` 引数を持たないすべての `chrome.exe` を `Default` とみなしています。

```csharp
// 現行コード（LauncherService.cs:68-69）
if (commandLine.Contains($"--profile-directory=\"{profileId}\"") || 
    (profileId == "Default" && !commandLine.Contains("--profile-directory")))
```

- **実態**: VS Codeの拡張機能（`--single-argument` 付き）やテスト用に別ディレクトリ（`--user-data-dir` 付き）で起動されたChromeも `--profile-directory` 引数を持たないため、`Default` プロファイルと誤認されていました。
- **影響**: 誤ったウィンドウにフォーカスしようとして失敗、または意図しないウィンドウが前面に来ていました。

### 問題2. 引数形式の厳格さ（Quote Sensitivity）
判定コードが `--profile-directory="{id}"` のようにダブルクォーテーション必須の完全一致となっていました。
- **実態**: 起動方法によってはクォーテーションが付かない場合があり（例: `--profile-directory=Default`）、その場合に一致しなくなっていました。

### 問題3. ウィンドウタイトル依存の脆弱性
ウィンドウの特定が `title.Contains("Google Chrome")` に依存しています（`LauncherService.cs` 90行目）。
- **影響**: 通常 Chrome のタイトルは `{ページタイトル} - Google Chrome` の形式ですが、この文字列への依存はタイトル形式の変更リスクを内包しています。

### 問題4. WMIクエリのパフォーマンス
プロセス検索に WMI（`Win32_Process`）を使用しており、実測で約5秒の応答遅延が発生していました。ユーザー操作のたびにこの遅延が発生するのは UX 上問題です。

### 問題5. 仕様との乖離（ProfileInfo の未使用プロパティ）
`ProfileInfo` モデルには `IsRunning`（bool）と `Hwnd`（**現在は `long` 型、→ 実装フェーズで `IntPtr` に変更予定**）プロパティが定義されています（`ProfileInfo.cs` 54-69行目）が、現在の `LauncherService` では一切使用されていません。仕様書（セクション4.5）では「起動時にhwndを記録、終了時に自動削除」と定義されていますが、この仕組みは未実装です。

## 設計・実現性調査フェーズ（対応方針決定）
調査結果に基づき、以下の対応方針を設計しました。

### 対応1. 正規表現による引数解析の導入
単なる文字列一致（`Contains`）ではなく、正規表現を使用してプロファイルIDを抽出します。

- **パターン**: `--profile-directory[= ]"?(.+?)"?(?:\s--|$)`
- クォーテーションの有無を吸収しつつ、スペースを含むプロファイルID（例: `Profile 1`）にも正しくマッチします。

> **注意**: 以前の案 `[^"\s]+` はスペースを含むIDにマッチしないため不適切でした。上記は修正後のパターンです。

### 対応2. ウィンドウクラス名による特定の安定化
ウィンドウタイトル文字列への依存をやめ、Win32 API の `GetClassName` を使用して、ウィンドウクラス名が `Chrome_WidgetWin_1` であることを判定条件とします。

- **Win32Api.cs への追加**: `GetClassName` の P/Invoke 宣言を追加。
- **併用条件**: クラス名が一致し、かつ `IsWindowVisible` で可視状態であることを確認。

### 対応3. 「Default」判定の厳格化
`--profile-directory` 引数がないプロセスを `Default` と判定する際、以下の追加条件を確認します。

- `--user-data-dir` 引数が**存在しない**こと（存在する場合は別のデータディレクトリを使用しているため対象外）。
- `--single-argument` 等の特殊引数で起動されたプロセスを除外すること。
- 標準のユーザーデータディレクトリ: `%LOCALAPPDATA%\Google\Chrome\User Data`

### 対応4. `SetForegroundWindow` の制約への対処
Windowsのセキュリティ制約により、`SetForegroundWindow` はバックグラウンドプロセスからの呼び出しでは失敗する場合があります。

- **対策**: `AttachThreadInput` を使用して、対象ウィンドウのスレッドと自プロセスのスレッドを一時的に関連付けてからフォーカスを実行します。
- **Win32Api.cs への追加**: `AttachThreadInput`, `GetForegroundWindow` の P/Invoke 宣言。`GetCurrentThreadId`（`kernel32.dll`）の P/Invoke 宣言も追加（`AttachThreadInput` の呼び出しに 自スレッドのIDが必要なため必須）。`GetWindowThreadProcessId` は既存のものを活用。

### 対応5. パフォーマンス改善方針（WMI ＋ PIDフィルタリングによる高速化 ＋ 方式Cキャッシュ）
C#標準APIでは他プロセスのコマンドライン引数を安全に取得できないため、**WMI（`ManagementObjectSearcher`）は引き続き使用します**。

ただし、現行のWMIクエリは全プロセスを解析するため約5秒かかります。以下の2段階アプローチにより、WMIを維持しながら大幅に高速化します。

#### 改善アプローチ：Process.GetProcessesByName ＋ PID絞り込みWMI

| ステップ | 手段 | 特性 |
| :--- | :--- | :--- |
| **① Chromeプロセスの一覧取得** | `Process.GetProcessesByName("chrome")` | 軽量・ミリ秒で完了 |
| **② コマンドライン引数の取得** | WMIを①で得たPIDに絞り込んでクエリ | 全プロセス解析を避けるため大幅に高速 |

```
// イメージ（実装ではない）
① pid一覧 = [1234, 5678, 9012]  ← Process.GetProcessesByNameで高速取得
② WHERE ProcessId=1234 OR ProcessId=5678 OR ProcessId=9012  ← 絞り込みWMIクエリ
```

この2段階アプローチにより、初回のWMI検索も大幅に短縮（数十〜数百ミリ秒程度）が見込まれます。

さらに、対応6で採用した方式C（ハイブリッドキャッシュ）の導入により、**WMI検索が走るのはキャッシュが存在しない場合（初回クリック時やChromeが一度閉じられた後）のみ**に限定されます。2回目以降はキャッシュされた `Hwnd` を検証するだけで即時フォーカスできるため、UX上のパフォーマンス問題は完全に解決されます。

### 対応6. ユーザー提案の「ハイブリッド方式」を含めたプロセス判定の比較検証
対象プロファイルのHwnd（ウィンドウハンドル）をどう管理・特定するかについて、3つの方式を比較検証しました。

#### 【方式A】起動記録・終了削除（仕様書原案）
- **概要**: 起動直後にHwndを取得し保持、プロセス終了イベント（Exited）を監視してHwndを破棄する。
- **課題**: Chrome特有のプロセス統合挙動により、起動プロセスと表示プロセスが分離しやすく追跡が困難。また、ランチャ外からの起動に対応できない。

#### 【方式B】都度検索方式（前回の提案）
- **概要**: ボタン押下のたびに全プロセスとコマンドラインを取得して検索する。状態は保持しない。
- **課題**: 常に対応可能だが、毎回プロセス走査のオーバーヘッド（処理時間）がかかる。

#### 【方式C】キャッシュ＋フォールバック（ユーザー提案のハイブリッド方式）
- **概要**: 
  1. Hwndを保持（キャッシュ）しておく。ボタンが押されたら、まず保持しているHwndが存在するか・有効かを確認し、有効ならフォーカスする。
  2. 無効な場合、または保持していない場合は、方式Bの「都度検索」を行い、見つかればフォーカスしてそのHwndを保持する。
  3. 検索しても見つからなければ、新しく起動する（起動直後はHwndの即時取得が困難なため保持せず、次回ボタン押下時に検索→保持される）。
- **利点**:
  - **超高速**: 一度Hwndを掴めば（2回目以降のクリックは）、全プロセス検索をスキップできるため一瞬でフォーカス可能。
  - **堅牢性**: キャッシュが無効（Chromeが閉じられた等）でも、すぐにプロセス検索にフォールバックするため失敗しない。ランチャ以外の場所から起動された場合も、最初の1回目のクリック時に全走査を行いHwndを掴むため問題なく対応できる。

#### 比較と採用判断
| 比較項目 | 方式A（記録・監視） | 方式B（都度検索） | 方式C（ハイブリッド） |
| :--- | :--- | :--- | :--- |
| **フォーカス速度** | 高速 | やや遅い | **超高速（キャッシュヒット時）** |
| **外部起動への対応** | 不可 | 可能 | **可能** |
| **実装の安定性**| 不安定（複雑な死活監視）| 安定 | **安定かつ高効率** |

**現時点の方針決定:**
ご提案いただいた **【方式C】（ハイブリッド方式）** は、パフォーマンス（速度）と堅牢性（状態不整合への耐性）を両立できる非常に優れたアプローチです。
OSの仕様上、閉じられたHwndと同じIDの数値が別のアプリに再利用される「Hwndの使い回しリスク」がごく稀に存在するため、キャッシュ確認時に「そのHwndが存在するか（`IsWindow`）」に加え、「そのクラス名がChromeのものか」という軽量な検証だけ挟むこととします。

これにより、**ご提案のロジック（ハイブリッド方式）を今回の実装のコアとして採用**いたします。

## 実装フェーズ（本計画書の段階では実施しません）
上記の方針C（ハイブリッド方式）を含めた設計に基づき、承認後に以下のファイルを修正します。

### [MODIFY] LauncherService.cs
- **`LaunchOrFocus` メソッドの刷新（方式Cの適用）**:
  1. `profile.Hwnd`（`IntPtr`型）に値がキャッシュされているか確認。
  2. キャッシュがある場合、`Win32Api.IsWindow` と `Win32Api.IsWindowVisible`、`Win32Api.GetClassName`（`Chrome_WidgetWin_1` か）で有効性を検証。
  3. 有効であれば、対象Hwndに対して `ShowWindow(hwnd, SW_RESTORE)` で最小化から復元し、フォーカスを当てて処理終了。
  4. 無効な場合、またはキャッシュがない場合は `FindWindowForProfile` でプロセスを走査。
  5. 走査で見つかったHwndは `ShowWindow(hwnd, SW_RESTORE)` で復元・フォーカスし、`profile.Hwnd = hwnd` で保存（キャッシュ更新）。
  6. 見つからなければ `Launch` を実行。
  - *(※ `ProfileInfo.IsRunning` については、状態同期の複雑化を避けるため今回のスコープでは連動を見送ります)*

- **`FindWindowForProfile` メソッドのプロセス検索ロジック刷新**:
  - WMIクエリ（`ManagementObjectSearcher`）は引き続きコマンドライン引数の取得に使用します。（※C#標準APIでは多プロセス引数取得が困難なため）。
  - ただし、方式Cの導入によりこの重い検索処理が走るのは「初回起動時（未キャッシュ時）」のみとなるため、実用上のパフォーマンスは劇的に改善されます。
  - 正規表現による正確なコマンドライン引数（プロファイルID）の抽出を適用。
  - `Default` プロファイル判定の厳格化（標準ディレクトリでの起動であるかの確認）。
  - 一致したPIDから `EnumWindows` を使用してウィンドウを探す既存の安全な仕組みは維持・最適化します。
- **フォーカス処理の安定化**:
  - `SetForegroundWindow` 呼び出し前に `AttachThreadInput` を実行し、バックグラウンドからのフォーカス失敗を防止。

### [MODIFY] Win32Api.cs
- `GetClassName` の P/Invoke 宣言を追加（Hwndのキャッシュ検証およびウィンドウ特定用）。
- `IsWindowVisible` の P/Invoke 宣言を追加（非表示のバックグラウンドウィンドウを弾くため重要）。
- `AttachThreadInput`（`user32.dll`）、`GetForegroundWindow`（`user32.dll`）の P/Invoke 宣言を追加。
- `GetCurrentThreadId`（`kernel32.dll`）の P/Invoke 宣言を追加（`AttachThreadInput` 呼び出しに必須）。
- `GetWindowThreadProcessId`、`IsWindow`、`ShowWindow`（SW_RESTORE）は既存の宣言を活用。

### [MODIFY] ProfileInfo.cs
- `Hwnd` プロパティの型を `long` から `IntPtr` に変更し、初期値を `IntPtr.Zero` に設定。
  - **理由**: Win32 API の型付け（`IntPtr`）と統一することで、不要な型キャストを排除しコードの可読性を向上させるため。

## 検証フェーズ
以下のテストシナリオを実施し、品質を確保します。

### 基本動作テスト
- **未起動状態**: ボタン押下で指定のプロファイルが正しく起動すること。
- **起動済み（プロファイル一致）**: ボタン押下で既存のウィンドウが前面に来ること。
- **起動済み（最小化中）**: ボタン押下でウィンドウが元のサイズに復帰し、前面に来ること。
- **複数プロファイル混在**: プロファイルAが起動中の状態でプロファイルBをボタンから起動し、それぞれが独立して制御（フォーカス/起動）されること。

### エッジケーステスト
- **Default プロファイル**: `Default` プロファイルが正しく判定・フォーカスされること。
- **スペース入りID**: `Profile 1` 等のスペースを含むプロファイルIDが正しく一致すること。
- **他アプリ起動のChrome混在**: VS Code等が起動したChromeウィンドウが存在する状態でも、正しいプロファイルのみが対象となること。
- **同一プロファイルの複数ウィンドウ**: 同じプロファイルで複数ウィンドウが開いている場合、いずれか1つにフォーカスが当たること。

### 既存機能の回帰テスト
- **自動テスト**: `dotnet test` による全14項目の通過を確認。
- **設定画面**: 並び替え・表示切替・保存が引き続き正常に動作すること。
