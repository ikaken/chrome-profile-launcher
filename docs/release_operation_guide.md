# リリース運用ガイドラインとトラブルシューティング履歴

本ドキュメントは、Chrome Profile Launcher のリリースプロセスにおける運用ルールおよび、過去のトラブル事例とその解決策を記録するものです。

## 1. リリース運用ルール
- **自動化の原則**: GitHub Actions (`release.yml`) を利用したビルド・パッケージング・リリースを行う。手動でのインストーラービルドは行わない。
- **ブランチ運用**: `feature/xxx` → `develop`（PR）→ `main`（PR）のフロー。`develop` から Pre-release、`main` から正式版リリース。
- **Pre-release**: `-beta` サフィックス付きタグは自動的に Pre-release として公開される（自動アップデート対象外）。
- **mainブランチへのプッシュ**: いかなる変更であっても、プッシュ直前に変更内容を提示し、ユーザーの明示的な承認を得ること。
- **README更新**: 正式版リリース作業の最後に、README.md のダウンロードリンクおよびバージョン情報を最新化する。

## 2. トラブル対応履歴: インストーラーアイコンの未反映 (#23)

### 事象
- 手動で `setup.iss` を修正・ビルドしても、GitHub Actions 経由のリリース版ではアイコンが反映されない。

### 原因
- **Velopack の仕様**: Actions 上では `setup.iss` を使用せず、`vpk pack` コマンドがパッケージングを行っているため、`setup.iss` の設定が無視されていた。
- **キャッシュ**: 本番環境の Windows OS および GitHub CDN のキャッシュにより、更新が反映されていないように見えていた。

### 解決策
- **ワークフローの修正**: `.github/workflows/release.yml` の `vpk pack` コマンドに `--icon` オプションを追加し、ビルドパイプライン内で明示的にアイコンファイルを指定するように変更した。
- **運用改善**: 修正反映を確実にするため、同一バージョンでのアセット上書きではなく、バージョンインクリメントを徹底することとした。

## 3. リリース時の確認チェックリスト

### Pre-release（develop ブランチから）
- [ ] `develop` が最新でクリーンであることを確認。
- [ ] Issue のラベルを確認し、バージョン番号を計算してユーザーの承認を得る。
- [ ] `-beta` サフィックス付きタグを作成・プッシュする。
- [ ] GitHub Actions の実行成功と Pre-release 公開を確認する。
- [ ] リリースノートを GitHub 上で編集する。

### 正式版リリース（main ブランチから）
- [ ] `develop` → `main` の PR マージ完了を確認。
- [ ] `main` が最新でクリーンであることを確認。
- [ ] Issue のラベルを確認し、バージョン番号を計算してユーザーの承認を得る。
- [ ] サフィックスなしのタグを作成・プッシュする。
- [ ] GitHub Actions の実行成功と Latest release 公開を確認する。
- [ ] README.md のダウンロード URL を新しいタグバージョンに書き換え、承認を得てプッシュする。
- [ ] リリースノートを GitHub 上で編集する。
- [ ] `gh issue close <number>` で対象 Issue をクローズする。
