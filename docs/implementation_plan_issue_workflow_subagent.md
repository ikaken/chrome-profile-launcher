# issue-workflow スキルのサブエージェント対応化 実施計画書

## 1. 目的
`issue-workflow` スキルをサブエージェント対応に拡張し、タスクの性質に応じたモデル（高度推論モデル vs 一般作業モデル）の使い分けを実現することで、効率と品質を両立させる。また、高度モデルのクォータ制限に対する運用的な回避策を定義する。

## 2. 役割分担とモデル構成

| 役割 | 担当ステップ | 使用モデル | 備考 |
| :--- | :--- | :--- | :--- |
| **Architect (メイン)** | Step 1, 4, 5, 9 | **gemini-3-flash-preview** | 要件分析、設計、高度な実装、ドキュメント同期を担当 |
| **Generalist (サブ)** | Step 0, 2, 3, 6, 7, 8, 10, 11 | **gemini-3.1-flash-lite-preview** | 環境チェック、Git操作、単純な記録、テスト、PR作成を担当 |
| **User (ユーザー)** | Step 4.5, 8.5 | - | 設計承認、実装・動作確認の最終判断 |

## 3. クォータ不足時のフォールバック戦略
Gemini CLIにはモデルの自動フォールバック機能がないため、以下の運用フローをスキルに定義する。

1. **検知**: 高度モデル（Architect）での実行中に `429 Too Many Requests` 等のクォータエラーが発生した場合、AIが即座に検知する。
2. **報告**: AIは現在の作業進捗とエラー内容を報告し、一般モデル（Generalist / gemini-3.1-flash-lite-preview）への切り替えをユーザーに提案する。
3. **実行**: ユーザーの同意を得た後、軽量モデルを使用してタスクを継続する。

## 4. 実施ステップ

### Step 1: `SKILL.md` の更新
- 役割分担（Architect / Generalist / User）の明記。
- `invoke_agent` を使用するタイミングと指示内容の定義。
- クォータエラー時のフォールバック・プロトコルの追記。

### Step 2: 動作検証
- 修正したスキルを用いて、実際のIssue対応フローが正しくサブエージェントに委譲されるかを確認する。

## 5. 完了条件
- `SKILL.md` が新しい役割分担とモデル構成に基づいて更新されていること。
- ユーザーによるレビューステップ（4.5, 8.5）が維持されていること。
- クォータエラー時の対応方針が明記されていること。
