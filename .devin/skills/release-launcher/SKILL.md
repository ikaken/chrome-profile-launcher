# Release Launcher

## 前提
`v*` タグをプッシュすると GitHub Actions が起動し、インストーラーのビルド・パッケージング・リリース作成を自動実行する。

## リリースフローの全体像

```
feature/xxx → develop (PR) → Pre-releaseタグ (v1.1.0-beta) → テスト
                                    ↓ 問題なければ
main (PR・マージ) → 正式版タグ (v1.1.0) → 自動アップデート
```

| タグ | ベースブランチ | リリース種別 | 自動アップデート |
|---|---|---|---|
| `v1.1.0-beta` | `develop` | Pre-release（手動DL） | ✖ 対象外 |
| `v1.1.0` | `main` | Latest release | ✔ 対象 |

## 承認ゲート（厳格）
- **タグ付け・プッシュ前**: バージョン番号をユーザーに提示し、明示的な承認を得るまで `git tag` / `git push` を実行しない。
- **README更新前**: 変更内容をユーザーに提示し、明示的な承認を得るまでコミット・プッシュしない。
- 承認とみなす言葉: 「タグを打ってください」「プッシュしてください」「進めてください」「OKです」等、**明示的に次の作業を指示する言葉**。バージョンの質問への返答や補足情報の提供は承認とみなさない。

## Pre-release フロー（develop ブランチから）
1. **事前準備**: `develop` ブランチが最新でクリーンであることを確認する。バージョン候補を決定しユーザーに提示する。サフィックスは必ず `-beta` を付ける（例: `v1.1.0-beta`）。
2. **タグ付け承認ゲート（承認必須）**: ユーザーが明示的に指示してから `git tag <バージョン番号>` を実行する。
3. **プッシュ**: `git push origin <バージョン番号>`。
4. **アクション監視**: GitHub Actions の完了と Pre-release の生成を確認する（`-beta` タグは自動的に Pre-release として公開される）。
5. **リリースノート編集**: GitHub上でリリース詳細を編集する。

## 正式版フロー（main ブランチから）
1. **事前準備**: `develop` → `main` の PR をユーザーがマージ完了後、`main` が最新でクリーンであることを確認する。バージョン候補を決定しユーザーに提示する（`-beta` なし）。
2. **タグ付け承認ゲート（承認必須）**: ユーザーが明示的に指示してから `git tag <バージョン番号>` を実行する。
3. **プッシュ**: `git push origin <バージョン番号>`。
4. **アクション監視**: GitHub Actions の完了と Latest release の生成を確認する。
5. **README更新承認ゲート（承認必須）**: 変更内容をユーザーに提示し、明示的な承認を得てからコミット・プッシュする。`README.md` のダウンロードリンクとバージョン表記を更新する。
6. **リリースノート編集**: GitHub上でリリース詳細を編集する。
7. **Issue クローズ**: `gh issue close <number>` で対象 Issue をクローズする。

## バージョンルール

プロジェクトは `v{major}.{minor}.{patch}-beta` 形式のセマンティック バージョニングを採用する。

| 位置 | 名前 | 変更条件 |
|---|---|---|
| 1番目 | **major** | ユーザーが明示的に指示した時のみ変更する。 |
| 2番目 | **minor** | 機能追加（`enhancement` タグ）の Issue に対応した時に変更する。minor が上がった場合、patch は `0` にリセットする。 |
| 3番目 | **patch** | バグ対応（`bug` タグ）の Issue に対応した時に変更する。 |

### バージョン決定の必須手順（省略禁止）

バージョン候補を決定する際は、必ず以下の順番で計算すること。推測・省略は禁止。

1. `git tag --sort=-version:refname` で**現在の最新タグ**を確認する。
2. 対応した Issue の**GitHubラベル**を `gh issue view <番号> --json labels` で確認する。
3. ラベルに応じて変更する位置を決定する:
   - `enhancement` → **minor を +1、patch を 0 にリセット**
   - `bug` → **patch を +1**
   - ユーザー明示指示 → **major を +1、minor・patch を 0 にリセット**
4. 計算結果をユーザーに提示し、承認を得る。

### 例
- 現在 `v0.2.0-beta`、`enhancement` タグ → minor +1、patch 0 → **`v0.3.0-beta`**
- 現在 `v0.1.16-beta`、`enhancement` タグ → minor +1、patch 0 → **`v0.2.0-beta`**
- 現在 `v0.1.16-beta`、`bug` タグ → patch +1 → **`v0.1.17-beta`**

## 注意事項
- 手動ビルドは不要。Actions が最新ソースをベースにパッケージングする。
- リリース前に `main` が最新状態であることを確認する。
- `main` ブランチへの変更はユーザー承認を得てから行う。
